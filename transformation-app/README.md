# 12-Week Transformation

A fat-loss and training dashboard built directly from
**`1700_Calorie_Indian_Cutting_Plan.xlsx`**. The Excel is the source of
truth for the meal plan, workout plan, targets, and grocery list — this app
turns it into a daily-use tracking product for your 84-day journey, with
plan-vs-actual logging, weekly aggregation, charts, a calendar, progress
photos, and full local persistence.

## The design system

The interface is a chunky, information-dense dashboard: summary numbers
first, detail underneath, and state encoded in shape as well as in the
figure. On desktop the app sits inside a 32px-radius shell — a dark nav rail
on the left, a light panel inset on the right that scrolls independently. On
mobile that shell dissolves into a single full-bleed column with a floating
bottom nav. One 12-column grid (`.dash` with `.c3`–`.c12` spans) drives both.

| Token | Role |
|---|---|
| `--ground` / `--panel` / `--surface` | Warm stone wash, content panel, cards |
| `--ink` / `--on-ink` | Near-black used for the rail, the feature card, and text |
| `--accent` `#ffd400` | Signal yellow — primary actions, and "you hit the target" |
| `--lav` / `--lav-fill` `#b9a7f2` | Lavender — the cool half of every two-series chart, and "in progress" |
| `--series-a/b/c` (+ `-on`, `-line`) | The three chart marks. `series-c` flips with the theme so it stays legible on either ground |
| `--red` | Semantic only: missed days and destructive actions |

Type is **Archivo** (variable, set expanded and heavy) for headlines and the
big figures, with **Instrument Sans** for every label, control and paragraph.
Both come from Google Fonts with real fallback stacks.

Everything is defined as custom properties in the bare `:root` block, then
redefined for `prefers-color-scheme: dark` (guarded so an explicit light
choice wins) and again for `:root[data-theme="dark"]` (so the in-app toggle
wins in both directions). Components only ever reference tokens, never
literals — which is why light and dark both hold together.

The dashboard-specific primitives live in `js/ui.js`: `bubbleChart()`
(circle-pack of the day's calories by macro), `dotGrid()` (the 84-day
consistency matrix), `barRow()`, `cardHead()`, `figure()` and `deltaPill()`.

**Nothing in your plan was invented.** Every meal, macro number, workout
day, grocery item and guideline comes straight from the workbook's five
sheets (`7-Day Meal Plan`, `Targets & Guidelines`, `Workout & Cardio`,
`Weekly Grocery List`, `12-Week Tracker`). Where the Excel didn't specify a
number — exact sets/reps/weights per exercise — the app leaves it for you
to enter rather than making one up.

## A note on the tech stack

The brief asked for React + TypeScript + Vite + Tailwind + Recharts. This
build uses **vanilla JavaScript (ES modules), hand-written CSS, and
Chart.js** instead, for one practical reason: the sandbox this app was
built in has no registry access (npm install is blocked by network policy),
so a Vite/npm toolchain couldn't actually be installed or built here.

The upside: this architecture needs **zero build step**. There's no
`node_modules`, no bundler config, nothing to install to run it locally —
open `index.html` through any static file server and it works. The code is
organized exactly like the requested architecture (`components` logic
lives in `pages/`, business logic in `utils/` and `data/`, persistence in
`storage/`, charts in `charts/`) with the same separation of concerns
you'd get from the React version. If you'd rather have it on React/Vite,
the module boundaries here map almost 1:1 onto components + hooks, so
porting is mechanical.

## Quick start

```bash
# From the project folder — any static server works:
python3 -m http.server 8080
# or: npx serve .
# or just open index.html directly in a modern browser (Chrome/Safari/Firefox)
```

Then open `http://localhost:8080`. That's the entire "install" and "dev"
process — there's no build step to run.

## Deployment

Any static host works, because the app is just static files:

- **Netlify / Vercel / Cloudflare Pages**: drag-and-drop the project folder, or point a git-based deploy at it. No build command needed (leave it blank, or `echo "no build"`).
- **GitHub Pages**: push the folder to a repo and enable Pages on the branch/root.
- **A single-file version**: `dist/bundle.js` (generated by `scripts/bundle.py`) is a bundled, dependency-free build of all the JS in one file, for contexts that need a single HTML file. See "Rebuilding the single-file bundle" below.

The app reads two external resources at runtime — Google Fonts
(Inter/Manrope) and Chart.js from cdnjs — both loaded via normal `<link>`/
`<script>` tags in `index.html`. Everything else is self-contained.

## Data model — how the Excel maps to the app

`scripts/extract_plan.py` reads the workbook and writes `js/data/planData.js`,
a plain JS object (`PLAN`) that's the single source of truth for plan data:

| Excel sheet | Becomes |
|---|---|
| `7-Day Meal Plan` | `PLAN.mealPlan[dayOfWeek]` — array of meals (id, meal type, food, quantity, calories/protein/carbs/fat/fiber, notes) |
| `Targets & Guidelines` | `PLAN.dailyTargets` (calorie/protein/fiber/water/veg/chocolate/whey ranges) + `PLAN.guidelines` (the free-text rows: cutting pace, food prep, fruit timing, etc.) |
| `Workout & Cardio` | `PLAN.workoutPlan[dayOfWeek]` — resistance label + exercise list, planned cardio, duration, rest/optional flags |
| `Weekly Grocery List` | `PLAN.grocery` (flat list) and `PLAN.groceryByCategory` (grouped) |
| `12-Week Tracker` | Not copied in — its columns (avg weight, waist, calories, protein, gym/cardio sessions, steps) are instead **computed live** from your daily logs by `js/utils/calculations.js` (`weekSummary`), since the sheet itself ships empty. |

The app keeps two datasets separate everywhere, per the brief:

- **PLAN** (`js/data/planData.js`) — read-only, from the Excel. Never mutated by the app.
- **Logs** (IndexedDB, one record per date) — everything you actually log: meal completion/skips/modifications, weight, steps, water, sleep, measurements, workout sets, cardio, journal entries, photos.

"Actual" nutrition totals for a day are built only from what's logged: a
completed meal counts the plan's own numbers, a modified meal counts what
you entered (falling back to the plan's number for any macro you left
blank), a skipped meal counts zero, and an unlogged meal is excluded
entirely (shown as pending, not zero) — see `actualTotals()` in
`js/utils/calculations.js`.

### How to modify the meal plan

Two ways:

1. **Edit the Excel and re-run the extractor** (recommended if you're changing a lot):
   ```bash
   pip install openpyxl
   python3 scripts/extract_plan.py /path/to/your-updated-plan.xlsx
   ```
   This overwrites `js/data/planData.js` with fresh data. It never touches your logged tracking data (that lives in IndexedDB, entirely separate).

2. **Hand-edit `js/data/planData.js` directly.** It's plain JSON-like JS — add/remove/edit entries in `PLAN.mealPlan.Monday`, etc. Each meal needs a unique `id` (used as the tracking key, so don't reuse an id for a different food once you've started logging against it).

### How to modify the workout plan

Same file, `PLAN.workoutPlan[dayName]`: `label` (e.g. "Upper body"),
`exercises` (a plain array of exercise names — the app builds an empty
3-set tracker for each one; add/remove sets from the UI), `cardio` (planned
cardio description), `duration`, and `isRestDay`/`isOptional` flags that
control whether the day is treated as mandatory.

### Daily consistency score

Each day gets a 0–100 score (`dailyScore()` in `calculations.js`), weighted
toward actually following the plan: meals 35%, resistance training 25%,
cardio 15%, water 15%, other logging (weight/steps) 10%. It's used for the
calendar's color coding, streaks, and weekly "Strong / Mixed / Needs
attention" badges. Tune the weights there if you want a different balance.

## Storage architecture

Everything persists in **IndexedDB** (`js/storage/db.js`), with a
transparent `localStorage` fallback if IndexedDB isn't available. Four
object stores:

- `settings` — one row: start date, starting/goal weight, daily targets, theme, units.
- `logs` — one row per date (`YYYY-MM-DD`), the full `DailyLog` (see JSDoc in `js/data/defaults.js`).
- `photos` — progress photos as data URLs, indexed by week number + angle.
- `grocery` — checked-item state per ISO week (so the list auto-resets weekly).

State lives in memory (`js/store.js`) and is hydrated from IndexedDB once
at boot; every mutation writes through to IndexedDB immediately and
triggers a re-render via a small pub/sub (`subscribe`/`notify`). There's no
virtual DOM — pages re-render by returning an HTML string from `render()`
and re-attaching event listeners in `mount()` after each render, which is
plenty fast at this app's scale (single user, a few hundred DOM nodes).

## Import / export / reset

Settings → Data:

- **Export JSON** — full backup (settings + every daily log + grocery state). Re-importable.
- **Export CSV** — a flat per-day summary (weight, waist, steps, water, sleep, workout/cardio status) for spreadsheet analysis.
- **Import backup** — merges a previously exported JSON file back in.
- **Reset all tracking data** — clears every log, photo and journal entry after a confirmation dialog. **Never touches `planData.js`** — your imported Excel plan survives a reset.

## Rebuilding the single-file bundle

`scripts/bundle.py` is a small, purpose-built ES-module bundler (no npm
dependency) that concatenates everything in `js/` into one script,
correctly handling the app's one circular import (`navigate`, shared
between the router and every page). Run it after changing any JS:

```bash
python3 scripts/bundle.py > dist/bundle.js       # all of js/ into one script
python3 scripts/build_artifact.py > artifact.html # + the CSS, as one HTML file
```

The multi-file `js/` tree is the real source — always edit there, not
`dist/bundle.js`.

## Testing

```bash
node scripts/simulate_journey.mjs
```

Simulates a full 84-day journey with varying adherence per phase and
asserts: all 12 weeks are disjoint and contiguous (no cross-week data
bleed), week 4/8/12 boundaries land on the correct 7-day windows, every
daily score stays within 0–100, and aggregation functions never throw.

## Accessibility

Semantic buttons/labels throughout, visible focus rings
(`:focus-visible`), no color-only status (every status also has a text
label/badge), large touch targets on mobile, and `prefers-reduced-motion`
is respected.

## Known simplifications

- Sets/reps/weight defaults to an empty 3-set tracker per exercise (add/remove freely) since the Excel doesn't specify numbers — by design, per the brief.
- Progress photos are stored as data URLs inside IndexedDB (fine for personal use on one device; for multi-device sync you'd want a real backend — the storage layer is isolated in `js/storage/db.js` specifically so that's a contained swap later).
- "12 Weeks" chart view and "Weekly" view both aggregate by week; "Daily" shows the last 14 days. Adjust the windows in `js/pages/progress.js` (`mountCharts`) if you'd like different ranges.
